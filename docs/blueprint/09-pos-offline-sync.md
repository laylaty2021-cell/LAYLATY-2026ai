# 09 — POS Offline / Sync Specification

## 1. لماذا Offline Mode

نقاط البيع (خاصة في القاعات والمواقع بعيدة التغطية) يجب أن تستمر بالعمل عند انقطاع الإنترنت، ضمن حدود مدروسة.

```
Online
 ↓
Local POS Cache
 ↓
Offline Transaction
 ↓
Local Queue
 ↓
Internet Returns
 ↓
Sync
 ↓
Server
```

## 2. ما يُسمح به Offline وما لا يُسمح

| العملية | مسموح Offline؟ | السبب |
|---|:---:|---|
| بيع نقدي (Cash Sale) | ✅ | لا يعتمد على طرف خارجي |
| بيع ببطاقة عبر جهاز دفع محلي متصل بشبكة مستقلة | ✅ (وفق دعم الجهاز) | |
| دفع إلكتروني عبر بوابة (Payment Gateway) | ❌ | يتطلب اتصالًا مباشرًا بالمزوّد لحظة الدفع |
| حجز مورد متزامن (Booking لحظي) | ❌ | يحتاج قراءة/كتابة فورية على Availability لمنع التعارض بين أجهزة متعددة |
| بيع منتج من المخزون المحلي المعروف مسبقًا | ✅ (بحد أقصى الكمية المخزَّنة محليًا وقت آخر مزامنة) | |
| إصدار فاتورة رسمية (ضريبية) | ⚠️ يُصدَر رقم مؤقت محليًا، يُستبدل برقم رسمي نهائي بعد المزامنة | لتفادي تكرار أرقام الفواتير بين أجهزة |

## 3. آلية المزامنة

```
POS Device
 ↓
Local DB
 ↓
Sync Queue
 ↓
API
 ↓
Server
 ↓
Conflict Resolver
```

كل عملية محلية تحمل:
```
device_id
local_transaction_id
server_transaction_id   -- فارغ حتى تتم المزامنة
created_at
sync_status              -- PENDING | SYNCED | CONFLICT | FAILED
```

نقطة النهاية: `POST /v1/stores/{store_id}/pos/sync` تستقبل دفعة (Batch) من العمليات المعلَّقة وتُرجع نتيجة كل عملية على حدة (راجع `PosTransactionSyncResult` في [`api/openapi.yaml`](../../api/openapi.yaml)).

## 4. منع التكرار أثناء المزامنة (Idempotency على مستوى الجهاز)

المفتاح المركّب:
```
device_id + local_transaction_id
```
مُطبَّق كقيد `UNIQUE` فعلي في `pos.pos_transactions` (راجع `db/schema.sql`). إذا أرسل الجهاز نفس العملية مرتين (بسبب انقطاع أثناء إرسال الاستجابة مثلًا)، يعيد الخادم نفس `server_transaction_id` السابق دون إنشاء عملية مكرّرة.

## 5. حل التعارضات (Conflict Resolver)

تعارض نموذجي: جهازان يبيعان آخر وحدة من نفس المنتج أثناء انقطاع الاتصال عن كليهما.

سياسة الحل:
1. **الأسبقية الزمنية بالخادم وليس بالجهاز** (ساعات الأجهزة غير موثوقة): أول عملية تصل للخادم وتنجح تخصيمًا من المخزون تُقبل.
2. العملية الثانية التي تكتشف نقص المخزون عند المزامنة تُعلَّم `CONFLICT` وتُعرض على الكاشير/المدير لحلّها يدويًا (تحويل لطلب توريد لاحق، اعتذار للعميل، أو تعديل الكمية).
3. لا تُرفض العملية بصمت — تظهر في لوحة "عمليات تحتاج مراجعة" حتى تُحل.

## 6. أمان الجهاز

- كل `terminal` مسجَّل مسبقًا (`pos.terminals.device_id`) بمفتاح API خاص بالجهاز (وليس بحساب المستخدم) — يسمح بإبطاله فورًا عند فقدان أو سرقة الجهاز دون التأثير على بقية الأجهزة.
- تُشفَّر قاعدة البيانات المحلية على الجهاز (SQLite/IndexedDB مع تشفير على مستوى الملف) لحماية بيانات العملاء والمعاملات المخزَّنة مؤقتًا.
