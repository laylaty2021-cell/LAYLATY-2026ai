# 20 — خارطة تنفيذ MVP → V1 → V2

## المبدأ

لا نبني كل شيء دفعة واحدة. الترتيب يعتمد على: (أ) ما يُثبت جدوى المنصة لأول شريحة تجار حقيقية، (ب) ما يفتح الطريق معماريًا لبقية القدرات دون إعادة كتابة لاحقًا.

## MVP (الإطلاق الأول)

**الهدف**: تاجر واحد (قاعة أو نشاط مشابه) يستطيع فعليًا: تسجيل متجره، تعريف خدمات/موارد، استقبال حجز، تحصيل دفعة، إصدار فاتورة، ورؤية قيد محاسبي أساسي.

| الوحدة | النطاق في MVP |
|---|---|
| Identity & Access | تسجيل/دخول، عضويات، أدوار نظامية جاهزة (بدون تخصيص أدوار من التاجر بعد) |
| Store/Branch | متجر واحد بفرع واحد (تعدد الفروع لاحقًا في V1) |
| Catalog | منتجات + خدمات أساسية (بدون Packages بعد) |
| Booking Engine | Resource + Availability + Booking lifecycle كاملة (بدون Packages مركّبة) |
| Order/Payment | دورة الطلب كاملة + مزوّد دفع واحد فقط + Idempotency |
| Inventory | حركات مخزون أساسية لمتجر بمستودع واحد (بدون تعدد مستودعات) |
| POS | نقطة بيع أونلاين فقط (بدون Offline Mode بعد) |
| Accounting | قيد مزدوج أساسي تلقائي عند اكتمال الطلب (بدون تقارير متقدمة) |
| Notifications | إشعار واحد أساسي لكل حدث رئيسي (Email/SMS فقط، بدون تفضيلات مخصصة) |
| RLS/Multi-tenant | مطبَّقة بالكامل من اليوم الأول (لا نؤجل الأمان) |
| Audit Log | مفعَّل لكل عملية حساسة من اليوم الأول |

**خارج نطاق MVP صراحة**: App Marketplace، Developer Portal، AI، POS Offline، تعدد الفروع، تعدد مزودي الدفع، اللوجستيات/النقل.

## V1 (بعد إثبات الجدوى مع أول مجموعة تجار)

- تعدد الفروع (Branch Scope كامل).
- تعدد المستودعات ونقل المخزون بينها.
- POS Offline/Sync الكامل (راجع [09](./09-pos-offline-sync.md)).
- Payment Adapter بأكثر من مزوّد + معالجة استرجاعات كاملة.
- Packages (باقات مركّبة من عدة خدمات/موارد).
- Webhooks خارجية (راجع [07](./07-webhooks.md)) — بدون Marketplace عام بعد، فقط تكاملات مباشرة يفعّلها فريق ليلتي للتجار الكبار.
- تقارير محاسبية أساسية (ميزان مراجعة، تقرير ضريبي قابل للتصدير).
- اللوجستيات: Fulfillment + Carrier Adapter للشحن التقليدي.

## V2 (توسّع المنصة)

- **App Marketplace + Developer Portal** كاملان (راجع [13](./13-app-marketplace.md), [14](./14-developer-portal.md)) — فتح المنصة لمطوّرين خارجيين.
- **Transportation Fulfillment** المتخصص لليلتي (مركبات، سائقون، رحلات — راجع نموذج `logistics.trips` في [`db/schema.sql`](../../db/schema.sql)).
- **AI Business Assistant** (قراءة فقط على بيانات المتجر) + **AI Marketplace** بحدود صلاحيات صارمة (راجع [13](./13-app-marketplace.md), القسم 5).
- فصل أول خدمة مستقلة عن الـ Monolith: **Payment Service** (أعلى حساسية ومتطلبات وثوقية/امتثال).
- تعدد المتاجر لنفس التاجر (Merchant بعدة Stores) بتقارير مجمّعة على مستوى التاجر.
- خيار Database-per-tenant للعملاء المؤسسيين (راجع [17](./17-deployment-architecture.md), القسم 6).

## معيار الانتقال بين المراحل

الانتقال من مرحلة لأخرى **ليس زمنيًا** (ليس "بعد 3 أشهر") بل **مبنيًا على معايير قبول**:
```
MVP → V1   : ≥ N متجر نشط فعليًا يستخدم الحجز + الدفع + POS أسبوعيًا بلا حوادث أمان/بيانات حرجة
V1  → V2   : استقرار تشغيلي مُثبت (SLA المراقبة في 19 مُحقَّق باستمرار) + طلب فعلي من تجار لتكاملات/تطبيقات خارجية
```

## اختبارات القبول لكل مرحلة (مختصر)

- **MVP**: سيناريو كامل من "إنشاء متجر" إلى "فاتورة مدفوعة مع قيد محاسبي صحيح" يعمل تلقائيًا في CI كاختبار End-to-End واحد لا ينكسر.
- **V1**: نفس السيناريو + مزامنة POS Offline بعد قطع اتصال متعمَّد في الاختبار + نقل مخزون بين فرعين.
- **V2**: تثبيت تطبيق طرف ثالث فعلي (حتى لو تجريبي داخلي) يستهلك Webhook وينفّذ كتابة محدودة النطاق ضمن Scope مصرَّح به فقط.
