# 15 — Multi-tenant Security Model

هذا المستند يجمع نموذج الأمان متعدد المستأجرين بشكل شامل (يربط بين 03، 04، وقرارات إضافية على مستوى التطبيق والبنية التحتية).

## 1. طبقات الدفاع (Defense in Depth)

```
1. API Gateway     — تحقق JWT + rate limiting + x-required-permission لكل مسار
2. Application     — تحقق صريح لـ store_id/branch_id من سياق الطلب قبل أي استعلام
3. PostgreSQL RLS  — عزل صف-بصف مستقل عن طبقة التطبيق (راجع 03)
4. Audit Log       — تسجيل كل عملية حساسة بعد وقوعها (كشف بعدي)
```

لا طبقة واحدة كافية بمفردها — الهدف أن يفشل أي اختراق أو خطأ برمجي في طبقة واحدة دون كشف بيانات متجر آخر.

## 2. عزل على مستوى الاتصال بقاعدة البيانات

- اتصال الـ API بقاعدة البيانات يستخدم دورًا (Role) بدون `BYPASSRLS`.
- `platform.current_user_store_ids()` تعتمد على `auth.uid()` المُستخرج من الـ JWT الموقّع من Identity & Access — لا تُمرَّر هوية المستخدم كـ Query Parameter عادي قابل للتلاعب.
- الاتصالات النظامية (Webhooks الواردة، مهام الخلفية، تقارير المنصة) تستخدم دورًا موثوقًا منفصلًا (Service Role) بصلاحيات محدودة ومُدقَّقة، وليس دورًا واحدًا "خارقًا" يُستخدم في كل مكان.

## 3. عزل التخزين والملفات

كل ملف مرفوع (صور منتجات، عقود، فواتير PDF) يُخزَّن بمسار يتضمن `store_id` صراحة (`/{store_id}/{resource_type}/{file_id}`)، وروابط الوصول المباشر (Signed URLs) محدودة الصلاحية زمنيًا (Pre-signed URL قصيرة الأجل)، لا روابط عامة دائمة لمحتوى خاص بمتجر.

## 4. عزل الأسرار (Secrets)

- بيانات اعتماد بوابات الدفع الخاصة بكل متجر (`integrations.credentials`) مشفّرة في قاعدة البيانات (Encryption at rest إضافي فوق تشفير القرص) بمفتاح مُدار عبر Secrets Manager، ولا Policy تسمح بقراءتها مباشرة من واجهة العميل (راجع 03، القسم 3).
- المفاتيح العامة للمنصة (JWT signing keys، مفاتيح تشفير قاعدة البيانات) لا تُشارَك أبدًا مع كود الواجهة الأمامية، ولا تظهر في أي Log.

## 5. الاختبار الأمني الإلزامي (قبل أي إطلاق)

1. اختبار تلقائي (CI) يحاول الوصول عبر حساب `Store A` لكل مسار API بمعرّف مورد يخص `Store B` — يجب أن يعيد `403/404` وليس البيانات.
2. اختبار مباشر على مستوى SQL: تسجيل دخول بدور محدود ومحاولة `SELECT` مباشر عابر للمتاجر يتحقق من عمل RLS دون المرور بالـ API إطلاقًا.
3. مراجعة يدوية لكل Endpoint جديد قبل الدمج (PR checklist) تتحقق من وجود `x-required-permission` في `openapi.yaml` ووجود Policy RLS مطابقة للجدول المستهدف.

## 6. حدود Branch Scope كأمان إضافي (وليس فقط UX)

تقييد الفرع (راجع [04](./04-roles-permissions-matrix.md), القسم 4) ليس مجرد فلترة عرض — هو مطبَّق أيضًا داخل RLS (مثال `pos.registers` في [`db/rls_policies.sql`](../../db/rls_policies.sql))، بحيث لا يستطيع موظف مقيَّد بفرع الوصول لبيانات فرع آخر حتى عبر استدعاء API مباشر متلاعَب به.
